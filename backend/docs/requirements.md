# Requirements

Labels: `FUNCTIONAL REQUIREMENT`, `ENGINEERING REQUIREMENT` (production practice needed for correctness/safety), `IMPLEMENTATION DECISION` (a specific choice made to satisfy a requirement).

Priority: `MUST` (blocks correctness or safety), `SHOULD`, `COULD`.

## Functional (REQ-F)

| ID | Requirement | Label | Priority | Acceptance criterion |
|---|---|---|---|---|
| REQ-F-001 | Ingest the 50-product catalog into a persistent ChromaDB collection as per-concern chunks (identity/variants/policy/care/faq) with metadata | FUNCTIONAL REQUIREMENT | MUST | Running the ingest script against `data/products.py` produces a ChromaDB collection whose document count equals the sum of chunks `product_to_chunks()` returns for all 50 products, verified by a script assertion. |
| REQ-F-002 | Retrieve relevant chunks for a query, gated by a calibrated similarity threshold, with optional `chunk_type`/`product_id` filters | FUNCTIONAL REQUIREMENT | MUST | `retrieve()` returns `None` for a query engineered to have no catalog answer (e.g. "do you have anything for a winter wedding?" against this build's actual catalog) and returns ≥1 chunk above threshold for a query with a known answer, in both cases confirmed by an automated test, not manual inspection. |
| REQ-F-003 | Generate a natural-language answer using retrieved evidence only; emit the exact fallback sentence when no evidence clears threshold | FUNCTIONAL REQUIREMENT | MUST | A test that removes/empties the retrieved context asserts the response equals the exact fallback contract (support-contact wording), and a Faithfulness-style check confirms no non-evidence product fact appears in an answer for a representative query. |
| REQ-F-004 | Expose `POST /ask` and `GET /health` HTTP endpoints matching `{question, session_id}` → `{answer, session_id}` | FUNCTIONAL REQUIREMENT | MUST | `curl -X POST /ask -d '{"question":"..."}'` run against the running service returns HTTP 200 with a JSON body containing both fields; `/health` returns HTTP 200. |
| REQ-F-005 | Metadata pre-filtering (`chunk_type`, `product_id`) to prevent near-duplicate policy/care chunks from competing at retrieval time | FUNCTIONAL REQUIREMENT | MUST | A test with two products sharing an identical return-policy sentence confirms a product-scoped query (`product_id=` set) returns only that product's policy chunk. |
| REQ-F-006 | Preserve the Indian-English occasion-vocabulary fix (e.g. "function") already present in `data/products.py` | FUNCTIONAL REQUIREMENT | MUST | A query containing "function" retrieves a festive-tagged product chunk in the top-3 results (regression test; the fix must not be silently dropped by future catalog edits). |
| REQ-F-007 | Deflect to support when retrieved context is about the right product but the wrong question type (threshold-adjacent type mismatch) | FUNCTIONAL REQUIREMENT | MUST | A query asking about an attribute zUdyog doesn't sell (e.g. jewellery) against a product chunk that clears threshold produces the fallback sentence, not an attempted answer, verified by test. |
| REQ-F-008 | For multi-intent queries ("festive AND warm"), answer from the best single-vector match with an explicit caveat rather than fail or fabricate a dual-match | IMPLEMENTATION DECISION (accepted limitation, not a defect) | COULD | Documented behavior only; no systematic multi-query retrieval is built. |
| REQ-F-009 | RAGAS evaluation harness (Faithfulness, Context Precision) against a labeled, pre-committed test set | FUNCTIONAL REQUIREMENT | MUST | `evaluation/evaluate.py` runs to completion and prints both scores for this build's provider/catalog, with the command and raw output saved under `docs/evidence/`. |
| REQ-F-010 | Empirically (re-)calibrate the similarity threshold for the actual 50-product catalog rather than reuse an unexamined default | ENGINEERING REQUIREMENT | MUST | A calibration script records top-1 similarity scores for ≥20 queries with known correct/incorrect catalog answers and documents the chosen threshold with the observed score gap, saved as evidence. |

## Non-functional (REQ-N)

| ID | Requirement | Label | Priority | Acceptance criterion |
|---|---|---|---|---|
| REQ-N-001 | No answer is ever produced without evidence that cleared the similarity threshold; absence always yields the exact fallback, never a guess | FUNCTIONAL REQUIREMENT | MUST | Fault-injection test: stub the retriever to return `None` and confirm the chain's output is byte-identical to the fallback string, for every entry point that calls it. |
| REQ-N-002 | Chat completion is deterministic (temperature fixed at 0, not exposed as a request-time parameter) | FUNCTIONAL REQUIREMENT | MUST | API schema / code review confirms `temperature` is not a field on `QuestionRequest`; `src/providers.py::get_chat_model()` hardcodes `temperature=0`, verified by `tests/test_prompt.py::test_chat_model_is_deterministic`. |
| REQ-N-003 | No secret (API keys) is ever committed to version control; `.env` is git-ignored from the first commit | ENGINEERING REQUIREMENT | MUST | `git log --all -- .env` is empty after the first commit; a secret-scan tool run over the repo reports no findings. |
| REQ-N-004 | Reject empty, >500-character, and prompt-injection-shaped input before it reaches retrieval or the model | FUNCTIONAL REQUIREMENT | MUST | API tests send all three malformed shapes and assert HTTP 422 (FastAPI/Pydantic validation error), none reaching the chain. |
| REQ-N-005 | The retrieval+LLM chain is constructed once at process startup, never per-request | FUNCTIONAL REQUIREMENT | MUST | Code review + a test that issues 2 concurrent requests and asserts the chain-builder function was invoked exactly once (via call-count mock). |
| REQ-N-006 | A collection built with one embedding model/dimensionality must never be silently queried with a different one — fail loudly, not silently, on dimension mismatch | ENGINEERING REQUIREMENT | MUST | An integration test that feeds a wrong-dimension query vector into the retriever raises an explicit, caught error rather than returning silently-wrong results. Defensive engineering independent of provider choice — protects against re-ingesting with a different embedding model later. |
| REQ-N-007 | ~~Default configuration runs at zero marginal API cost via a local model~~ — **REMOVED (ADR-010)** | IMPLEMENTATION DECISION | N/A | Local-model support was removed from the codebase entirely at the user's request; there is no free/local fallback path in this build. This requirement no longer applies — kept in the table, struck through, rather than silently deleted, so the traceability history stays legible. |
| REQ-N-008 | Treat customer question/answer text as sensitive by default; do not log raw question/answer bodies at a verbosity enabled in production, no payment/account data collected by MUST-scope endpoints | ENGINEERING REQUIREMENT | SHOULD | Structured log review shows request IDs and metadata but not full question/answer text at default log level. |
| REQ-N-009 | Structured logs include a request ID; health/readiness endpoint exists; errors are tracked distinguishably from normal 200s | ENGINEERING REQUIREMENT | MUST | `/health` returns 200 with a body; a request through `/ask` produces a log line containing a request ID correlatable to the response. |
| REQ-N-010 | `/ask` has a basic rate limit to bound cost/abuse exposure | ENGINEERING REQUIREMENT | SHOULD | A test issuing requests above the configured limit from one client receives HTTP 429 after the threshold. |
| REQ-N-011 | Coverage floor of 80% on core logic (chunker, retriever, prompt-contract, API validators) | ENGINEERING REQUIREMENT | MUST | Coverage report (`pytest --cov`) for `src/chunker.py`, `src/retriever.py`, `src/prompt.py`, `src/api.py` validators shows ≥80%, saved as evidence; any shortfall is stated explicitly, not hidden. |

## Technical (REQ-T)

| ID | Requirement | Label | Priority | Acceptance criterion |
|---|---|---|---|---|
| REQ-T-001 | Python project with pinned `requirements.txt`, isolated via venv, including `pytest`, `pytest-cov`, `ragas`, `datasets` | ENGINEERING REQUIREMENT | MUST | `pip install -r requirements.txt` into a clean venv succeeds with no resolver errors; `pip freeze` matches the committed file. (A single-command install fails on an unrelated `langchain-community`/`ragas` conflict, ADR-008 — the documented two-step install in `README.md` is the actual working path.) |
| REQ-T-002 | Cached OpenAI client factory module (`src/providers.py`) — the single place that constructs embeddings/chat clients | IMPLEMENTATION DECISION | MUST | `src/providers.py::get_embeddings()`/`get_chat_model()` are the only call sites that import `langchain_openai`; cached via `lru_cache` (REQ-N-005). |
| REQ-T-003 | ChromaDB `PersistentClient` at `./chroma_db`, collection `zudyog_products`, `hnsw:space=cosine` | FUNCTIONAL REQUIREMENT | MUST | Inspecting the collection's metadata after creation shows `hnsw:space: cosine`. |
| REQ-T-004 | Local containerized run via Docker Compose | ENGINEERING REQUIREMENT | SHOULD | `docker compose up` brings up the API container and it responds to `/health`, evidence captured. |
| REQ-T-005 | Railway deployment file (`Procfile`) with the standard `uvicorn` start command | ENGINEERING REQUIREMENT | COULD (files only — deploying itself is `NOT-VERIFIED`, no Railway account in this environment) | `Procfile` content matches `web: uvicorn src.api:app --host 0.0.0.0 --port $PORT`; tagged NOT-VERIFIED in traceability. |
| REQ-T-006 | No changes required to the existing `zudyog-fashion` Next.js frontend — its `/api/chat` route already forwards `{question, session_id}` to `${SHOPBOT_API_URL}/ask` | FUNCTIONAL REQUIREMENT (integration constraint) | MUST | Running the frontend with `SHOPBOT_API_URL=http://localhost:8000` and submitting a chat message produces a rendered answer with zero backend-contract edits. |
| REQ-T-007 | Automated test suite: unit, integration (real ChromaDB, not mocked), API, negative/failure, security (injection), AI evaluation, and at least one mutation/fault-check per core concept | ENGINEERING REQUIREMENT | MUST | `pytest` run reports pass/fail/skip counts and coverage, saved as evidence; at least one test explicitly breaks a core concept (e.g. empties the retrieved context) and confirms the corresponding test fails without the fix in place. |

## Explicitly deferred (not requirements for this build)
Hybrid search / re-ranking, Qdrant Cloud migration, Answer Relevance & Context Recall RAGAS dimensions, multi-query retrieval, corrective retrieval, conversation memory, response caching.
