# Requirements

Labels: `BOOK REQUIREMENT` (the book states or necessitates this), `ENGINEERING REQUIREMENT` (production practice the book doesn't mention but correctness/safety needs), `IMPLEMENTATION DECISION` (a specific choice made to satisfy a requirement).

Priority: `MUST` (core book concept / blocks correctness or safety), `SHOULD`, `COULD`.

## Functional (REQ-F)

| ID | Requirement | Concept(s) | Label | Priority | Acceptance criterion |
|---|---|---|---|---|---|
| REQ-F-001 | Ingest the 50-product catalog into a persistent ChromaDB collection as per-concern chunks (identity/variants/policy/care/faq) with metadata | C-008,C-009,C-010,C-011 | BOOK REQUIREMENT | MUST | Running the ingest script against `data/products.py` produces a ChromaDB collection whose document count equals the sum of chunks `product_to_chunks()` returns for all 50 products, verified by a script assertion. |
| REQ-F-002 | Retrieve relevant chunks for a query, gated by a calibrated similarity threshold, with optional `chunk_type`/`product_id` filters | C-005,C-006,C-012,C-013,C-014 | BOOK REQUIREMENT | MUST | `retrieve()` returns `None` for a query engineered to have no catalog answer (e.g. "do you have anything for a winter wedding?" against this build's actual catalog) and returns ≥1 chunk above threshold for a query with a known answer, in both cases confirmed by an automated test, not manual inspection. |
| REQ-F-003 | Generate a natural-language answer using retrieved evidence only; emit the exact fallback sentence when no evidence clears threshold | C-002,C-015,C-016,C-017 | BOOK REQUIREMENT | MUST | A test that removes/empties the retrieved context asserts the response equals the book's fallback contract (support-contact wording), and a Faithfulness-style check confirms no non-evidence product fact appears in an answer for a representative query. |
| REQ-F-004 | Expose `POST /ask` and `GET /health` HTTP endpoints matching `{question, session_id}` → `{answer, session_id}` | C-018,C-019,C-020 | BOOK REQUIREMENT | MUST | `curl -X POST /ask -d '{"question":"..."}'` run against the running service returns HTTP 200 with a JSON body containing both fields; `/health` returns HTTP 200. |
| REQ-F-005 | Metadata pre-filtering (`chunk_type`, `product_id`) to prevent near-duplicate policy/care chunks from competing at retrieval time | C-009 | BOOK REQUIREMENT (elevated from book's "SHOULD" — book calls this a *future* concern at 5 products; this build's real catalog has 50 products, so the competing-chunk failure the book describes is reachable now, not hypothetical) | MUST | A test with two products sharing an identical return-policy sentence confirms a product-scoped query (`product_id=` set) returns only that product's policy chunk. |
| REQ-F-006 | Preserve the Indian-English occasion-vocabulary fix (e.g. "function") already present in `data/products.py` | C-024 | BOOK REQUIREMENT | MUST | A query containing "function" retrieves a festive-tagged product chunk in the top-3 results (regression test; the fix must not be silently dropped by future catalog edits). |
| REQ-F-007 | Deflect to support when retrieved context is about the right product but the wrong question type (threshold-adjacent type mismatch) | C-026 | BOOK REQUIREMENT | MUST | A query asking about an attribute zUdyog doesn't sell (e.g. jewellery) against a product chunk that clears threshold produces the fallback sentence, not an attempted answer, verified by test. |
| REQ-F-008 | For multi-intent queries ("festive AND warm"), answer from the best single-vector match with an explicit caveat rather than fail or fabricate a dual-match | C-025 | BOOK REQUIREMENT (explicitly an accepted Book 1 limitation, not a defect) | COULD | Documented behavior only; no systematic multi-query retrieval is built (that is named Book 2 scope). |
| REQ-F-009 | RAGAS evaluation harness (Faithfulness, Context Precision) against a labeled, pre-committed test set | C-022,C-023 | BOOK REQUIREMENT | MUST | `evaluation/evaluate.py` runs to completion and prints both scores for this build's provider/catalog, with the command and raw output saved under `docs/evidence/`. |
| REQ-F-010 | Empirically (re-)calibrate the similarity threshold for the actual 50-product catalog rather than reuse the book's 5-product-derived 0.75 unexamined | C-013 (U-01) | ENGINEERING REQUIREMENT | MUST | A calibration script records top-1 similarity scores for ≥20 queries with known correct/incorrect catalog answers and documents the chosen threshold with the observed score gap, saved as evidence. |

## Non-functional (REQ-N)

| ID | Requirement | Concept(s) | Label | Priority | Acceptance criterion |
|---|---|---|---|---|---|
| REQ-N-001 | No answer is ever produced without evidence that cleared the similarity threshold; absence always yields the exact fallback, never a guess | C-002,C-004 | BOOK REQUIREMENT | MUST | Fault-injection test (framework §11): stub the retriever to return `None` and confirm the chain's output is byte-identical to the fallback string, for every entry point that calls it. |
| REQ-N-002 | Chat completion is deterministic (temperature fixed at 0, not exposed as a request-time parameter) | C-016 | BOOK REQUIREMENT | MUST | API schema / code review confirms `temperature` is not a field on `QuestionRequest`; repeated identical requests against the Ollama path return identical answers in a test run. |
| REQ-N-003 | No secret (API keys) is ever committed to version control; `.env` is git-ignored from the first commit | Ch2 | BOOK REQUIREMENT | MUST | `git log --all -- .env` is empty after the first commit; a secret-scan tool run over the repo reports no findings. |
| REQ-N-004 | Reject empty, >500-character, and prompt-injection-shaped input before it reaches retrieval or the model | C-019 | BOOK REQUIREMENT | MUST | API tests send all three malformed shapes and assert HTTP 422 (FastAPI/Pydantic validation error), none reaching the chain (verified via mock/spy). |
| REQ-N-005 | The retrieval+LLM chain is constructed once at process startup, never per-request | C-020 | BOOK REQUIREMENT | MUST | Code review + a test that issues 2 concurrent requests and asserts the chain-builder function was invoked exactly once (via call-count mock). |
| REQ-N-006 | Swapping the embedding/LLM provider (OpenAI ↔ Ollama) must not require changing retriever/chain call sites, and must fail loudly (not silently) on embedding-dimension mismatch against an existing collection | C-012; Ch2 dimension warning | ENGINEERING REQUIREMENT | MUST | A unit test asserts the retriever module exposes the same `retrieve()` signature regardless of `LLM_PROVIDER`; an integration test that points a 768-dim-configured retriever at a 1536-dim collection (or vice versa) raises an explicit, caught error rather than returning silently-wrong results. |
| REQ-N-007 | Default configuration runs at zero marginal API cost (Ollama); OpenAI is opt-in and requires the user's own funded key | Ch2 "Free Alternative"; ADR-001 | IMPLEMENTATION DECISION | MUST | `.env.example` defaults `LLM_PROVIDER=ollama`; running the full ingest+ask flow with no `OPENAI_API_KEY` set succeeds end-to-end. |
| REQ-N-008 | Treat customer question/answer text as sensitive by default; do not log raw question/answer bodies at a verbosity enabled in production, no payment/account data collected by MUST-scope endpoints | framework §0 default; U-06 | ENGINEERING REQUIREMENT | SHOULD | Structured log review shows request IDs and metadata but not full question/answer text at default log level. |
| REQ-N-009 | Structured logs include a request ID; health/readiness endpoint exists; errors are tracked distinguishably from normal 200s | framework §9 Observability | ENGINEERING REQUIREMENT | MUST | `/health` returns 200 with a body; a request through `/ask` produces a log line containing a request ID correlatable to the response. |
| REQ-N-010 | `/ask` has a basic rate limit to bound cost/abuse exposure | framework §9 Security (book is silent on this) | ENGINEERING REQUIREMENT | SHOULD | A test issuing requests above the configured limit from one client receives HTTP 429 after the threshold. |
| REQ-N-011 | Coverage floor of 80% on core logic (chunker, retriever, prompt-contract, API validators) | framework §11 | ENGINEERING REQUIREMENT (ENGINEERING-DECISION: floor = 80%, matching framework's suggested default) | MUST | Coverage report (`pytest --cov`) for `src/chunker.py`, `src/retriever.py`, `src/prompt.py`, `src/api.py` validators shows ≥80%, saved as evidence; any shortfall is stated explicitly, not hidden. |

## Explicitly deferred (not requirements for this build)
Hybrid search / re-ranking, Qdrant Cloud migration, Answer Relevance & Context Recall RAGAS dimensions, multi-query retrieval, corrective retrieval, conversation memory, response caching — all named by the book as Book 2/3 scope (see `docs/book/unknowns.md`, `docs/book/concept-ledger.md`).
